# Викладення правил доступу з CI — що зроблено й що лишилося

Правила Firestore (`firebase/firestore.rules`) і індекси
(`firebase/firestore.indexes.json`) тепер викладає прогін на кожен пуш у
`main`, перед розгортанням сайту. Доти це був ручний крок —
`npm run deploy:rules`.

**Чому це важить більше, ніж виглядає.** Проєкт Firebase тут **один на всі
сайти шкіл**, тож `firestore.rules` описує шляхи всіх з них. Розходження між
файлом і базою означає не «одна сторінка зламалась», а «межа доступу не та,
яку читали в рев'ю». А побачити це розходження не було чим: `check:rules`
ганяє 29 випадків на **емуляторі**, тобто зелений гейт доводить, що файл
правильний, і мовчить про те, що приймає `promo-web-hub`.

## Крок, який лишилося зробити: видати права

**Ключа замало.** Ключ каже, *хто* стукає; що йому можна — кажуть ролі, і
типовий ключ Firebase Admin SDK прав на викладення правил **не має**. Це
виміряно на сусідньому `Slovko`, де той самий за походженням ключ упав двічі
поспіль: спершу на `serviceusage`, потім — уже після видачі першої ролі — на
`firebaserules`.

1. відкрити
   <https://console.cloud.google.com/iam-admin/iam?project=promo-web-hub>
2. знайти рядок `firebase-adminsdk-fbsvc@promo-web-hub.iam.gserviceaccount.com`;
3. олівець (**Edit principal**) праворуч;
4. **ADD ANOTHER ROLE** і додати всі три ролі з таблиці (поле пошуку приймає
   і назву, і ідентифікатор);
5. **SAVE**.

Ролей саме три, бо стільки дій робить рядок
`--only firestore:rules,firestore:indexes`:

| Що викладається | Роль у консолі | Ідентифікатор |
|---|---|---|
| `firebase/firestore.rules` | Firebase Rules Admin | `roles/firebaserules.admin` |
| `firebase/firestore.indexes.json` | Cloud Datastore Index Admin | `roles/datastore.indexAdmin` |
| — (перевірка, що API увімкнені) | Service Usage Consumer | `roles/serviceusage.serviceUsageConsumer` |

Останній рядок не відповідає жодному файлу й саме тому забувається: перед
викладенням `firebase-tools` питає в Google, чи ввімкнено
`firestore.googleapis.com`, і це питання вимагає власного дозволу — тобто
падіння приходить ще до першого правила.

Realtime Database тут немає, тож ролі `roles/firebasedatabase.admin`, яка є в
сусідніх проєктах, не треба.

> **Чому не `Owner`.** Він теж спрацює — і саме тому його тут немає. Ключ
> лежить у секретах GitHub, тож права ключа — це права кожного, хто може
> змінити воркфлоу. Три вузькі ролі вміють рівно те, що робить прогін, і не
> читають даних користувачів.

## Перевірити

```bash
gh run list -R Alik532UA/teatralo4ka.odesa.ua --workflow deploy.yml --limit 1
```

Джоб `publish-rules` має бути **зеленим**, і в ньому два кроки, а не один:
«Викласти правила й індекси» та «У базі справді те, що в git». Другий читає
правила з бази назад і звіряє з файлом, бо успішний `deploy` доводить лише те,
що команда не впала.

## Якщо ключ доведеться замінити

1. <https://console.firebase.google.com/project/promo-web-hub/settings/serviceaccounts/adminsdk>
   → **Generate new private key**;
2. покласти в секрет однією командою (шлях свій):

```bash
gh secret set FIREBASE_SERVICE_ACCOUNT -R Alik532UA/teatralo4ka.odesa.ua < "C:/Users/alik5/Downloads/promo-web-hub-firebase-adminsdk-xxxxx.json"
```

3. **видалити завантажений файл** — у секретах уже є копія, а на диску це
   ключ від бази відкритим текстом.

Ролі при заміні ключа не губляться: вони видані сервісному акаунту, а не
конкретному ключу.

## Що тут НЕ налаштовується

Публічний конфіг Firebase (`apiKey`, `projectId` тощо) сюди не входить: він
лежить літералами в `src/lib/firebase/config.ts`, у git
(SECURITY-v9 § 4.2.1, `SEC-CONFIG-IN-SOURCE`). Ані змінних, ані секретів для
нього не треба — `git clone && npm run dev` працює без жодного налаштування.

Єдине справді секретне значення проєкту — `VITE_APPCHECK_DEBUG_TOKEN`: він
обходить перевірку App Check цілком, тож живе лише в локальному `.env` і лише
в режимі `DEV`. У налаштуваннях репозиторію його немає й не має бути.
